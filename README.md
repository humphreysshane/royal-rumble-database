# WWE Royal Rumble Database

The most comprehensive, sourced, statistical database of WWE Royal Rumble
matches ever built — modeled on Opta / Stathead / Baseball Reference for
pro wrestling. Every entrant, entry number, elimination, and record is
tagged for exactly how solid it is (`CONFIRMED`, `DERIVED`, `PROBABLE`,
`UNCERTAIN`, `CONFLICTING`, `UNKNOWN`) rather than presented as uniformly
reliable, and every non-derived fact carries a source citation. Genuine
disagreements between sources are preserved and logged in `data/flags.csv`,
never silently resolved by guessing.

**Live dashboard:** `dashboard/` — a self-contained static site (no server,
no build step to view it) with full event/elimination timelines, a sortable
career stat leaderboard, entry-number analytics, and a cross-division World
Map of wrestler nationalities. If this repo is served over GitHub Pages, the
dashboard is at `<pages-url>/dashboard/`. Locally, just open
`dashboard/index.html` in a browser.

## Repository structure

```
data/                    — the source of truth. Every table is a plain CSV.
  wrestlers.csv             one row per person, ever
  events.csv                one row per Royal Rumble match
  entrants.csv               one row per (event, wrestler) — the core table
  eliminations.csv           one row per elimination, in match order
  sources.csv                every source consulted, with a reliability tier
  flags.csv                  open questions, conflicts, known gaps — read this
  derived/                   computed tables — NEVER hand-edit these, they are
                              regenerated by scripts/build_derived.py
scripts/
  schema.py                  column definitions + the status vocabulary
  build_derived.py           recomputes every table under data/derived/
  build_dashboard_data.py    builds dashboard/data.json from data/
  validate_integrity.py      referential-integrity + schema checks — run this
                              before trusting any change
  build_YYYY*.py              one-off scripts that built each event, kept as
                              a record of how that event's data was assembled
dashboard/
  index.html / page.html     the dashboard's HTML+JS (single file, no deps)
  data.json                  generated — do not hand-edit, rebuild it instead
DEFINITIONS.md             — the rules this whole project runs on. Read this first.
BUILD_INSTRUCTIONS.md      — full spec for adding new events to the database
DEEP_RESEARCH_INSTRUCTIONS_20260928.md — current open research brief
ROADMAP.md                 — chronological log of every major change and why
IDEAS.md                   — brainstormed stats/features not built yet
docs/BUILD_LOG.md          — detailed year-by-year research/build history
edit/                      — browser-based data editor (see below)
logger/                    — Royal Rumble Event Logger, a local tool for
                              reviewing eliminations against footage
```

## Editing this yourself

**Option A — the browser data editor** (`edit/index.html`, served at
`<pages-url>/edit/` if this repo is on GitHub Pages, or just open the file
locally): pick a table, edit it as a spreadsheet with schema-aware dropdowns
for status/boolean columns, and it opens the result as a normal pull request
against this repo — no local setup, works from any device. It talks to
GitHub's API directly from your browser using a personal access token you
supply and it keeps client-side (instructions are on the page itself). It
blocks saving on a duplicate primary key but doesn't replicate every check
`validate_integrity.py` does — run that before merging, same as any other
change.

**Option B — edit the CSVs directly**, same as always:

1. Edit CSVs in `data/` directly (a spreadsheet app, a text editor, or a
   script — whatever's convenient). Never invent a value to fill a blank
   cell; leave it empty and, if it's a real open question, add a row to
   `data/flags.csv`.
2. Run `python3 scripts/build_derived.py` to recompute every derived table
   (career totals, records, entry-number stats, etc.).
3. Run `python3 scripts/validate_integrity.py data` — fix anything it flags
   before moving on.
4. Run `python3 scripts/build_dashboard_data.py data dashboard/data.json` to
   refresh the dashboard.
5. Open `dashboard/index.html` locally to sanity-check the result before
   committing.

Requires Python 3, no external packages.

**Reviewing eliminations against footage:** see `logger/README.md` — a
local tool (`git clone` this repo, `cd logger`, run two Python scripts) for
going through every recorded elimination one at a time against your own
video, with every field pre-populated and a review workflow that turns into
a pull request the same way the data editor does.

## For an AI working on this repo

Read `DEFINITIONS.md` first — it's the fixed rulebook (status vocabulary,
source-reliability tiers, key term definitions) every existing row already
follows. Then `BUILD_INSTRUCTIONS.md`, which is written specifically for an
AI or person doing a "full handoff" build directly against these files (the
standard this project has used for its external-research passes to date).

The non-negotiables, restated: the CSVs in `data/` are the only source of
truth — never edit `data/derived/*.csv` by hand, they're generated. Never
invent a value to fill a gap; leave it blank. A `CONFIRMED` status requires
two independent sources; log disagreements in `flags.csv` instead of picking
one silently. Run `scripts/validate_integrity.py` after any change and don't
consider a change done until it passes clean. If you're adding an event, use
an existing `scripts/build_20XX*.py` file as a template for the expected
shape and rigor.
